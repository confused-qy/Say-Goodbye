# 《临终关怀》双程序分工文档

> 依据：《游戏流程》当前版本  
> 团队配置：程序 A、程序 B  
> 目标：先完成可从开场走到结局的完整流程，再集中打磨三个小游戏与表现。

## 1. 当前需求状态

### 已确定内容

- 核心场景：安宁医院（病房左侧、病房右侧）、林姨家（客厅、卧室）。
- 通用交互：点击调查、拖拽使用道具、物品栏、密码锁、对话、场景切换。
- 心愿一：信息卡与生日密码、志愿者来访、吉他编曲、磁带与歌词合成、电话、遗憾碎片。
- 心愿二：化妆、向日葵开花解谜、钥匙与收纳盒、胭脂、遗憾碎片。
- 结局：四格漫画、三个月后空病房、播放录音笔后结束。

### 待修改／未锁定内容（原文黄色高亮）

- 医院与林姨家的美术场景方案。
- 心愿三的完整设计，包括女儿来访、做饭时序、电话、全家福拼图和碎片获得规则。
- “首次游玩”和“提前完成拼图”的判定描述存在歧义，需要策划确认是否允许玩家提前接触拼图。

处理原则：待定内容只做通用接口和低成本灰盒，不在需求确认前制作强绑定流程的代码。

## 2. 总体分工

| 人员 | 主责方向 | 主要交付 |
| --- | --- | --- |
| 程序 A | 游戏主流程与场景交互 | 流程状态机、存档、场景切换、点击交互、道具逻辑、对话/漫画/结局串联 |
| 程序 B | UI、音频与小游戏 | 物品栏、提示与界面框架、吉他/化妆/向日葵/拼图小游戏、电话与音频播放 |

公共原则：谁负责模块，谁负责该模块的场景预制体、脚本、配置数据、调试入口和自测；不要让同一个场景文件成为两人的长期共同编辑对象。

## 3. 程序 A 任务

### A1. 项目基础与主流程

- 建立场景目录与加载规则，建议每个区域使用独立场景或独立 Prefab。
- 实现 `GameFlowManager`：管理序章、三个心愿、回忆、结局等流程节点。
- 流程推进使用配置或事件条件，不把整段剧情写成一个巨大脚本。
- 实现存档：当前流程节点、已收集道具、已完成谜题、已看对话、音量设置。
- 提供“新游戏、继续游戏、清除存档”和开发用章节跳转。

### A2. 通用场景交互

- 点击热点：查看、拾取、打开、播放、拨号、进入小游戏。
- 场景切换：病房左/右、客厅、卧室，以及待定的走廊/厨房。
- 可交互物状态：未发现、可交互、已完成；处理彩色/灰色或高亮表现。
- 密码柜、带锁收纳盒、电话、录音机、磁带播放机、镜子等场景机关。
- 道具合成与使用判定：空白磁带 + 歌词、钥匙 + 收纳盒、胭脂 + 镜子等。

### A3. 剧情落地

- 串联心愿一和心愿二的全部流程条件。
- 接入对话数据，负责对话结束后触发流程事件。
- 实现漫画序章、结局四格漫画及三个月后尾声。
- 实现“集齐遗憾碎片 → 进入结局”的统一判定。
- 心愿三确认后，负责其剧情节点、场景条件和主流程接入。

### A4. 给程序 B 的接口

- `StartMinigame(id)`：启动指定小游戏。
- `OnMinigameFinished(id, result)`：接收小游戏成功、失败或退出结果。
- `AddItem(id)`、`RemoveItem(id)`、`HasItem(id)`：统一道具接口。
- `RaiseStoryEvent(id)`：电话、对话、动画或场景变化等剧情事件。
- `IsNodeCompleted(id)`：查询剧情/谜题完成状态。

## 4. 程序 B 任务

### B1. 通用 UI 与音频

- 物品栏：展示、选中、拖拽、道具详情、合成反馈；数据来源使用程序 A 的道具接口。
- 对话框、提示框、心愿清单、密码输入框、暂停菜单和基础设置界面。
- 通用小游戏容器：打开、关闭、成功、失败、重试及返回主场景。
- 电话界面与来电提示；录音、磁带、环境音和 UI 音效的播放控制。

### B2. 心愿一小游戏

- 吉他编曲：琴弦依次亮起/震动、音符输入、正确性校验、成功反馈。
- 关卡内容使用配置数据保存，便于修改提示顺序和答案。
- 成功后只返回结果，不直接修改剧情状态或发放关键道具。

### B3. 心愿二小游戏

- 化妆小游戏：先实现一种最终确认的操作模式；另一种模式需求锁定后再做。
- 妆容部件/深浅参数配置化，完成全妆后回传成功事件。
- 向日葵谜题：点击自身及左右相邻花朵切换状态、胜利检测、重置。
- 提供可调整的花朵数量与初始状态，避免谜题答案写死在 UI 中。

### B4. 心愿三（需求待定）

- 需求确认前只制作可复用灰盒：食材拖拽、处理区、锅具槽位、计时/步骤校验。
- 拼图使用独立配置：图片、行列数、拼片初始位置、吸附阈值。
- 不在小游戏内部决定“是否提前完成”“发放哪个碎片”；由主流程判定。
- 心愿三文本确认后，程序 B 完成做饭与拼图正式版，程序 A 接入剧情。

## 5. 目录与协作约定

建议目录：

```text
Assets/
├── Art/
├── Audio/
├── Data/
│   ├── Dialogue/
│   ├── Items/
│   └── Minigames/
├── Prefabs/
│   ├── Interaction/
│   └── UI/
├── Scenes/
│   ├── Main/
│   ├── Areas/
│   └── Minigames/
├── Scripts/
│   ├── Core/          # 程序 A 主责
│   ├── Interaction/   # 程序 A 主责
│   ├── UI/            # 程序 B 主责
│   └── Minigames/     # 程序 B 主责
└── Docs/
```

- 两人各自使用独立 Git 分支，建议命名为 `feature/core-flow`、`feature/minigames-ui`。
- 每次提交只包含一个明确功能；提交前确认没有提交 `Library`、`Temp`、`Logs`。
- 场景冲突高发：主流程场景由程序 A 维护；程序 B 使用独立小游戏场景/Prefab，再由程序 A 接入。
- ScriptableObject 等配置文件也指定单一维护人，另一人通过代码读取，不同时编辑。
- 公共接口变更先在文档或群聊中确认，合并接口提交后再分别开发。

## 6. 推荐开发顺序

### 里程碑 1：可跑通灰盒

- 程序 A：场景切换、点击交互、流程状态、道具与存档。
- 程序 B：物品栏、对话框、小游戏容器。
- 联调结果：能用占位资源从序章走到结局，各环节可通过开发按钮跳过。

### 里程碑 2：完成心愿一、二

- 程序 A：完整串联两条心愿剧情与场景机关。
- 程序 B：吉他、化妆、向日葵三个小游戏以及音频反馈。
- 联调结果：正常游玩可获得前两个遗憾碎片，退出重进后状态正确。

### 里程碑 3：心愿三与结局

- 先锁定黄色高亮需求，再开始正式实现。
- 程序 A：心愿三剧情、条件判定、结局入口。
- 程序 B：做饭与全家福拼图正式版。
- 联调结果：三颗碎片获取顺序正确，不会重复领取或提前进入结局。

### 里程碑 4：整合与发布

- 替换正式美术和音频，统一交互提示与转场。
- 全流程测试、存档兼容测试、分辨率适配、音量与性能检查。
- 制作最终构建并保留可快速定位章节的测试版本。

## 7. 合并前验收清单

- 模块能从独立测试入口运行，也能被主流程调用。
- 成功、失败、退出、重复进入均有明确行为。
- 剧情关键道具不可重复获得或错误消耗。
- 切换场景及退出游戏后，已完成状态能够恢复。
- UI 在目标分辨率下无严重遮挡，拖拽操作有清晰反馈。
- Console 无新增 Error；关键异常有可读日志。
- 新增资源路径、事件 ID 和配置字段已同步给另一位程序。

## 8. 需要策划尽快确认的问题

1. 心愿三最终保留哪些场景：走廊、厨房是否制作独立背景？
2. 女儿电话、来到病房、进入回忆三者的准确触发顺序是什么？
3. 做饭是否要求严格步骤/时间，做错后如何重试？
4. 拼图何时首次开放，“提前完成拼图”具体指什么？
5. 心愿三碎片的正式名称与获得动画是什么？
6. 化妆小游戏最终采用滑动条还是多选部件，是否需要失败条件？
7. 黄色高亮的两张美术场景是待替换图片，还是场景结构也会修改？
